# Trends and change observations

`/trends` and `/api/trends` summarize retained canonical blocks by timestamp in rolling 24-hour, 7-day and 30-day windows, plus 30 UTC calendar days. Pool attribution is recomputed with the current registry; unknown blocks remain in the denominator. Wilson 95% intervals quantify sampling uncertainty only. Blocks with future timestamps are excluded until their timestamp is reached. Coverage uses the oldest retained block timestamp, not a promise of accurate wall-clock timestamps. Source freshness is separate from historical coverage.

The VPS retains up to 10,080 blocks and gradually backfills them using the existing bounded collector batches. This is a block limit, not a guaranteed number of days. Canonical resets rebuild retained history; trends then show partial coverage. No synthetic historical points are created.

The change feed polls consenting public onboarding listings after collector polls. The first snapshot records “First observed” at tracking time. Later status transitions are persisted in `public_changes`, with only operator listing identity and status strings. Public responses omit the internal identity and filter against current listing consent. No credentials, contacts, configuration or message bodies are copied. The feed does not yet track manual connection reviews or rating changes. Reports can become stale without a pool being offline. Observation time is not the exact event time; short transitions between polls may be missed. Retention is 90 days, with the latest 30 currently visible observations shown. Initial baseline metadata and current status survive restarts.

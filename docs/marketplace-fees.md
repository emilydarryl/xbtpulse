# Private marketplace fee pilot

This implementation is disabled by default. The public marketplace still uses its existing direct-payment workflow. A separate private source snapshot and SQLite database run under `/opt/xbtpulse-payments/fee-pilot`, on VPS loopback `127.0.0.1:4318`. No public proxy route points to it. Test agreements in that database are synthetic, not customer sales.

## Policy and screens

New orders created while `MARKET_FEES_ENABLED=true` snapshot `seller-success-v1`: 2% of the agreed total including delivery, calculated with integer satoshis and rounded upward once. The seller explicitly accepts the exact quote alongside payment instructions. Orders created while disabled never acquire a fee later. The order page shows the quote before acceptance and its separate status afterward; the seller desk exposes the same private order view. Detailed payment guidance stays on `/market/payments`.

The seller owes the fee after the buyer records completion. Purchase funds go directly to the seller's wallet. Only the seller receives the platform-fee checkout link; no signing key or wallet connection is requested. This fee is not deducted from the purchase amount, enforced by escrow or impossible to bypass. Trades arranged outside the flow can avoid collection.

Open issues pause collection and hide checkout. Cancelled requests owe no fee. An invoice already issued may still receive payments after its link is hidden or it expires. The reconciliation process retains it and checks late settlement. Buyer-confirmed full sale refunds create `refund_due` for an already paid fee, preserving the original credit. Support must review and arrange the actual refund separately; the app cannot send it. Partial refunds require manual discussion. Unknown/exceptional receipts remain in review rather than being declared waived.

Default on-chain invoice threshold: 600 sats, configurable upward, never below 546. A smaller quoted fee is not collected in this pilot. This does not replace it with a 600-sat charge. The dedicated store must use **Never add network fee**, zero payment tolerance and the reviewed confirmation target. The sender's own wallet transaction fee is separate from the invoice amount. Lightning and pooled small-fee billing are not implemented.

## Configuration and access

Environment fields are documented in `.env.example`: `MARKET_FEES_ENABLED`, `MARKET_FEE_API_ORIGIN`, `MARKET_FEE_CHECKOUT_ORIGIN`, `MARKET_FEE_STORE_ID`, `MARKET_FEE_API_KEY`, `MARKET_FEE_WEBHOOK_SECRET`, `MARKET_FEE_ALLOW_LOOPBACK`, `MARKET_FEE_MIN_INVOICE_SATS`. Use a dedicated store-scoped key with **only** `btcpay.store.cancreateinvoice` and `btcpay.store.canviewinvoices`. Never grant wallet, signing, broadcasting, invoice modification, store administration or Lightning access. Keep keys and HMAC secrets out of the repository, URLs, browser storage and logs.

HTTPS is required except an explicitly enabled loopback-only private pilot. The browser checkout origin can differ from the authenticated API origin, but returned checkout paths must match the expected origin and exact invoice ID before rewriting the origin. The current private pilot uses API `127.0.0.1:23000`, checkout operator forward `127.0.0.1:23300`, and market operator forward `127.0.0.1:23301`. The two forwards travel over SSH. Local forward ports are not publicly reachable services. The pilot Compose template is [here](../experiments/market-payments/fee-pilot-compose.yaml); source snapshots and secret environments are prepared privately, not automatically by that template.

`POST /api/market/fees` requires the seller capability, matching seller/order, allowed Origin and JSON. It performs an explicit invoice-status check. Private order GETs read cached SQLite state and never call XBTPay. Both fee endpoints return 404 while disabled. `POST /api/market/fee-webhook` accepts bounded raw bytes with a valid `BTCPay-Sig` HMAC, supported event type and matching store/invoice. No orphan order is created from a callback. No real webhook is registered in the current pilot; its generated secret is reserved for later controlled delivery testing.

## Accounting and recovery

Tables: `market_order_fees`, `market_fee_credits`, `market_fee_payment_refs`, `market_fee_callbacks`. Invoice/order/credit/payment-reference uniqueness prevents duplicate attribution. One durable POST intent is committed before invoice creation. A lost response is recovered by store/order lookup; an ambiguous missing invoice does not cause another POST. Multiple matching invoices, changed quotes, wrong metadata/asset/value, manual settlement and exceptional payments enter review. Expired invoices require support review; automatic replacement could cause duplicate payment and is deliberately absent.

Authenticated reads validate immutable order metadata, store, currency, method, exact amount and settled underlying payment references before credit. Each chain payment reference can credit only one fee invoice. Browser redirects and signed notifications are not payment evidence by themselves. A confirmed payment that later regresses retains its historical credit and enters review; it is not silently erased. Full-sale refunds are checked locally on restart, including after ordinary invoice polling ages out, so an offline payment service cannot suppress the refund obligation.

One background batch handles up to four invoices every 30 seconds, ordered by last check. Ordinary polling covers seven days after invoice creation; authenticated callbacks mark older records for recheck, and the seller can explicitly request a check. Network/service failures retain a durable retry, including older callback-triggered checks after restart. This is a small-pilot queue, not unlimited reconciliation capacity. Without callback delivery, older unexpected payments require an explicit check/support review. Fee records are deleted with orders after the existing 180-day retention window. XBTPay and backups have separate retention; this is not a permanent general ledger or financial reporting system. Review these limits before scaling.

Preserve private source/configuration, both payment databases, the pilot SQLite database and its WAL-consistent backup, plus the approved API key. Revoking that key in XBTPay stops the pilot's invoice access; it does not cancel invoices, stop chain monitoring or invalidate receiving addresses. To stop only this pilot: `docker compose -p xbt-market-fee-pilot stop` from its directory. Do not stop unrelated marketplace or mining services. Restart with the same private environment/data; do not generate replacement invoices as a recovery shortcut.

## Evidence and remaining gates

The Node suite covers exact quotes, seller acknowledgement, capability/Origin gates, cancellations/issues/minimums, callback authentication/replay, lost POST replies, duplicate payment references, restart persistence, reorg review, refunds after polling expiry, retention and real HTTP route behavior. Browser checks covered required acceptance and the seller fee panel in a clearly labeled simulation. Real XBTPay tests verified exactly two key permissions, denial of settings/wallet reads, one unpaid exact-amount invoice, repeated lookup of that same invoice, durable ledger recovery with zero credits, rejection of the earlier non-fee receipt and the actual settled-payment JSON schema. The receipt display fix separately passed 31 targeted XBT Release tests and live receipt verification.

Still required: an owner-funded fee invoice with automatic credit and restart/database recovery; an explicitly authorized fee-refund and recovery trial; real authenticated callback delivery; public HTTPS checkout connectivity; encrypted off-server backups and compatible spending-wallet restore; operational refund/support procedures. No fee funds, customer purchase funds, escrow funds or Lightning funds moved in these integration checks. Do not enable public collection merely because an invoice can be created. Escrow and Lightning remain separate, unverified integrations.
